# SamaLine — سامانه نظرسنجی و فرم‌ساز آنلاین

سامانه‌ی SaaS نظرسنجی، پرسشنامه، فرم‌ساز و آزمون‌ساز با پشتیبانی کامل از فارسی و RTL.
شرح کامل محصول، نقشه‌ی راه و گزارش ممیزی در [todo.md](todo.md).
فهرست امکاناتی که هنوز ساخته نشده‌اند: [REMAINING.md](REMAINING.md).

> **راه‌اندازی روی سرور:** بخش [استقرار روی سرور](#استقرار-روی-سرور) — یک دستور.

## اجرا بدون Docker

پروژه به‌صورت خوداتکا اجرا می‌شود: دیتابیس پیش‌فرض **SQLite** است و به‌صورت یک فایل
داخل `backend/data/` ساخته می‌شود. هیچ سرویس بیرونی (Postgres، Redis، Docker) لازم نیست.

پیش‌نیاز: فقط Node.js نسخه‌ی ۲۰ به بالا.

```bash
# ۱) بک‌اند
cd backend
npm install
cp .env.example .env      # در ویندوز: copy .env.example .env
npm run db:seed           # اختیاری: ساخت اسکیما و بازنشانی پلن‌ها به پیش‌فرض
npm run start:dev         # http://localhost:3000
```

مستندات API (Swagger): `http://localhost:3000/api/docs`

```bash
# ۲) پنل مدیریت
cd panel && npm install && npm run dev          # http://localhost:5174

# ۳) رندر فرم برای پاسخ‌دهنده
cd form-renderer && npm install && npm run dev  # http://localhost:5173
```

سپس در پنل ثبت‌نام کنید، یک فرم بسازید، «انتشار لینک» را بزنید و لینک عمومی را باز کنید.

## اجرای نسخه‌ی تولید

```bash
cd backend
npm install
cp .env.example .env
npm run release     # بیلد + مهاجرت و داده‌ی اولیه + اجرا
```

فرانت‌اندها را بیلد و با هر وب‌سروری سرو کنید:

```bash
cd panel && npm install && npm run build           # خروجی در panel/dist
cd form-renderer && npm install && npm run build   # خروجی در form-renderer/dist
```

> پیش از انتشار، `JWT_SECRET`، `RESPONDENT_KEY_SALT` و
> `SECRET_ENCRYPTION_KEY` را حتما عوض کنید و `PAYMENT_PROVIDER` را از
> حالت محلی خارج کنید.

### دود تست

```bash
cd backend && npm run smoke
```

چرخه‌ی کامل سامانه را روی سرور در حال اجرا می‌سنجد: ثبت‌نام، ساخت فرم با
منطق و شاخص، انتشار، لینک اختصاصی، Piping، پنهان شدن سوال شرطی، ثبت
پاسخ، گزارش، خروجی، مخاطبان، کمپین، مسدودسازی SSRF و احراز هویت
پاسخ‌دهنده، داشبوردساز، پرداخت، جداسازی سازمان‌ها و بررسی سلامت — ۳۲ گام.
نشانی سرور با `BASE` داده می‌شود (پیش‌فرض `http://localhost:3000/api/v1`).

## معماری

```
backend/         NestJS + TypeORM
  forms/         موتور منطق (اعتبارسنجی + زمان اجرا) و موتور شاخص
  public/        رندر فرم، پیمایش صفحات، ثبت پاسخ
  messaging/     لایه‌ی سرویس‌دهنده پیامک/ایمیل، صف، کمپین
  contacts/      دفترچه مخاطبان و اتصال به سرویس‌های بیرونی
  plans/         سیاست پلن و سقف مصرف
  reports/       داشبورد و گزارش‌گیری
panel/           پنل مدیریت (React + Vite)
form-renderer/   اپ سبک پاسخ‌دهنده (React + Vite)
```

**منطق فرم فقط یک پیاده‌سازی دارد و آن سمت سرور است.** رندرر برای هر گام،
صفحه و سوالات قابل نمایش را از سرور می‌گیرد؛ پاسخ به سوالی که پنهان بوده
هنگام ثبت حذف می‌شود.

## اتصال به نرم‌افزارهای دیگر

اگر فهرست افراد در یک CRM، سامانه‌ی منابع انسانی یا باشگاه مشتریان است،
می‌توان آن را مستقیم به دفترچه مخاطبان وصل کرد (منوی «اتصال به CRM»):

۱. نشانی API، هدر احراز هویت و مسیر آرایه در پاسخ را می‌دهید.
۲. نام کلیدهای پاسخ را به فیلدهای سامانه نگاشت می‌کنید (فیلد تو در تو با نقطه: `profile.phone`).
۳. با «پیش‌نمایش» چند رکورد اول را می‌بینید، بعد ذخیره و همگام‌سازی می‌کنید.

شماره‌ی موبایل خودکار یکسان‌سازی می‌شود (`+98`، `0098`، ارقام فارسی و عربی،
جداکننده‌ها) و کلیدهای نگاشت‌نشده به متغیر شخصی‌سازی پیام تبدیل می‌شوند.
همگام‌سازی دوباره رکورد تکراری نمی‌سازد و مخاطب موجود را به‌روز می‌کند.

> **امنیت:** سرور به نشانی‌های شبکه داخلی، لوکال‌هاست و سرویس متادیتای ابری
> درخواست نمی‌زند (محافظت SSRF)، و تغییر مسیر را دنبال نمی‌کند. برای سرویسی
> که واقعا داخل شبکه‌ی سازمان است `ALLOW_PRIVATE_CONTACT_SOURCES=true` را
> تنظیم کنید. کلید API در پاسخ‌های پنل برگردانده نمی‌شود.

## لینک ثابت و اختصاصی فرم

هر فرم یک لینک توکنی پیش‌فرض دارد که همیشه معتبر می‌ماند. در تب «ساخت فرم»
می‌توان یک نشانی خواندنی هم گذاشت:

```
http://localhost:5173/f/0904bbb1011e6027010b77861ce67795   ← پیش‌فرض
http://localhost:5173/f/nazarsanji-1405                    ← اختصاصی
```

نشانی اختصاصی ثابت می‌ماند و برای بروشور، بنر و پیامک مناسب است. افزودن آن
لینک‌های پخش‌شده‌ی قبلی را نمی‌شکند، چون هر دو راه معتبرند.

## دیتابیس

| حالت | تنظیم | توضیح |
|---|---|---|
| پیش‌فرض (توسعه و On-Premise سبک) | `DB_DRIVER=sqlite` | فایل `backend/data/samaline.sqlite`؛ اسکیما خودکار ساخته می‌شود |
| تولید | `DB_DRIVER=postgres` + `DATABASE_URL` | مایگریشن‌های `src/database/migrations/` را دستی اجرا کنید |

نوع ستون‌ها در `backend/src/database/column-types.ts` بین دو درایور نگاشت می‌شود
(`jsonb`↔`simple-json`، `timestamptz`↔`datetime`، `ILIKE`↔`LIKE`).

## سرویس‌های بیرونی — همه اختیاری

هر سرویس بیرونی یک پیاده‌سازی پیش‌فرض خوداتکا دارد، پس سامانه بدون هیچ
حساب یا کلیدی کامل کار می‌کند. با یک متغیر محیطی به سرویس واقعی وصل می‌شود.

| سرویس | پیش‌فرض خوداتکا | جایگزین واقعی |
|---|---|---|
| پیامک | `local` — نوشتن در `data/outbox/sms.jsonl` | `kavenegar` یا `webhook` |
| ایمیل | `local` — نوشتن در `data/outbox/email.jsonl` | `webhook` |
| هوش مصنوعی | `mock` — بدون کلید و بدون اینترنت | `openai` (هر سرویس سازگار، شامل مدل داخلی) |
| درگاه پرداخت | `local` — هر پرداختی موفق، فقط برای توسعه | `zarinpal` |
| صف ارسال | صف پایدار روی دیتابیس + صف درون‌فرایندی | — (نیازی به Redis نیست) |

خروجی مدل هوش مصنوعی همیشه پیش از بارگذاری در فرم‌ساز با schema
اعتبارسنجی می‌شود؛ ساختار نامعتبر رد می‌شود.

> ارسال انبوه از صف پایدار عبور می‌کند و با ری‌استارت سرور از بین
> نمی‌رود. برداشتن کار برای یک نمونه‌ی سرور امن است؛ اجرای چندنمونه‌ای
> به قفل ردیف نیاز دارد.

## دستورهای بک‌اند

```bash
npm run start:dev    # اجرا با watch
npm run typecheck    # بررسی نوع‌ها
npm test             # ۵۱۷ تست واحد و ادغام
npm run smoke        # دود تست چرخه‌ی کامل روی سرور در حال اجرا
npm run release      # بیلد + داده‌ی اولیه + اجرای تولید

npm run reset-2fa -- you@example.com    # خاموش کردن ورود دومرحله‌ای (گوشی گم‌شده)
```

تست‌های ادغام روی SQLite در حافظه اجرا می‌شوند، پس رفتار واقعی دیتابیس
سنجیده می‌شود بدون نیاز به هیچ سرویسی. یک تست هم مطمئن می‌شود اسکیمای ساخته‌شده
با مهاجرت‌ها دقیقا همان است که موجودیت‌ها می‌خواهند؛ فراموش کردن مهاجرت برای
ستون تازه همان‌جا شکست می‌خورد نه روی سرور.

## مدیر کل سامانه (سوپرادمین)

نقشی فرامستاجری برای گرداننده‌ی سکو، جدا از نقش‌های سازمانی (owner/admin/…).
فقط تنظیمات سراسری را کنترل می‌کند و به داده‌ی سازمان‌ها دسترسی نمی‌دهد.

تعیین و لغو، فقط از خط فرمان سرور:

```bash
cd backend
npm run superadmin -- user@example.com           # تعیین
npm run superadmin -- user@example.com --revoke  # لغو
npm run superadmin -- --list                     # فهرست
```

هیچ اندپوینتی برای ارتقای خود وجود ندارد؛ وگرنه هر کاربری می‌توانست خودش را
مدیر کل کند. گارد دسترسی هم عمداً از دیتابیس می‌خواند نه از ادعای درون توکن،
تا لغو نقش بلافاصله اثر کند و منتظر انقضای توکن قبلی نماند.

**نوار پایین فرم‌ها:** متن و نشانی و روشن/خاموش بودن نوار پایین همه‌ی فرم‌های
عمومی از «تنظیمات سامانه» در پنل تنظیم می‌شود. صاحبان فرم به آن دسترسی ندارند.
پیش‌فرض: «شرکت سماع رایانه کیش» با پیوند به kishwifi.com.

## استقرار روی سرور

ساده‌ترین و پایدارترین راه: **یک سرور لینوکسی، یک دستور.** بدون Docker، بدون
nginx و بدون سرویس دیتابیس جداگانه — یک پروسه‌ی Node که با systemd روشن می‌ماند.

پیش‌نیاز: سرور لینوکسی (اوبونتو/دبیان پیشنهاد می‌شود)، دسترسی root، Node.js
نسخه‌ی ۲۰ به بالا، و git. حداقل ۱ گیگ رم و ۲ گیگ دیسک آزاد.

```bash
git clone https://github.com/kish210/SamaLine.git /opt/samaline
cd /opt/samaline
bash scripts/deploy.sh                                   # پورت پیش‌فرض ۸۰۸۰
PORT=9000 bash scripts/deploy.sh                         # پورت دلخواه
PUBLIC_URL=https://survey.example.com bash scripts/deploy.sh   # با دامنه
```

اسکریپت روی خودِ سرور همه‌چیز را می‌سازد: وابستگی‌ها (دقیقا نسخه‌های قفل‌شده،
با `npm ci`)، build هر سه بخش، فایل تنظیمات با کلیدهای تصادفی، سرویس systemd و
باز کردن پورت در فایروال؛ و در پایان تا بالا آمدن سلامت سامانه صبر می‌کند.
اگر پورت پیش‌فرض اشغال باشد، اولین پورت آزاد بعدی انتخاب می‌شود. اگر Node روی
سرور نباشد، با `ALLOW_NODE_INSTALL=1` خودش نصب می‌کند.

`PUBLIC_URL` نشانی‌ای است که کاربران فرم را با آن باز می‌کنند؛ لینک‌های پیامک،
ایمیل، یادآوری و وبهوک تلگرام از روی آن ساخته می‌شوند. اگر ندهید، `http://IP:PORT`
گذاشته می‌شود.

**یک پورت برای همه‌چیز:** خودِ بک‌اند فایل‌های ساخته‌شده را هم سرو می‌کند.

| نشانی | چیست |
| --- | --- |
| `PUBLIC_URL/` | فرم‌های عمومی (`/f/<token>`) و کیوسک (`/k/<token>`) |
| `PUBLIC_URL/panel` | پنل مدیریت |
| `PUBLIC_URL/api/docs` | مستندات API |
| `PUBLIC_URL/api/v1/health` | بررسی سلامت (برای پایشگر بیرونی) |

### چک‌لیست پس از اولین نصب

۱. در پنل ثبت‌نام کنید، سپس خودتان را مدیر کل سامانه کنید:
   ```bash
   cd /opt/samaline/backend && npm run superadmin -- you@example.com
   ```
۲. در پنل، «تنظیمات ← ورود دومرحله‌ای» را برای حساب مدیر کل روشن کنید.
۳. پلن سازمان‌ها را از «تنظیمات سامانه ← سازمان‌ها و پلن‌ها» تعیین کنید. ثبت‌نام
   تازه با پلن رایگان شروع می‌شود و ارتقا فقط از همین‌جاست.
۴. برای پیامک واقعی در `backend/.env`: `SMS_PROVIDER=kavenegar`،
   `KAVENEGAR_API_KEY` و `KAVENEGAR_SENDER`؛ سپس `systemctl restart samaline`.
۵. پوشه‌ی `backend/data/backups/daily` را گه‌گاه به جای دیگری (خارج از سرور) کپی کنید.

### HTTPS (پیشنهادی برای دامنه)

سامانه خودش HTTP است. برای HTTPS ساده‌ترین راه Caddy است که گواهی را خودکار
می‌گیرد و تمدید می‌کند. فایل `/etc/caddy/Caddyfile`:

```
survey.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

سپس `systemctl enable --now caddy` و یک بار
`PUBLIC_URL=https://survey.example.com bash scripts/deploy.sh`. با nginx هم همین
کار شدنی است؛ سامانه IP واقعی کاربر را از پراکسیِ روی همان سرور می‌پذیرد.

```bash
cd /opt/samaline && bash scripts/update.sh
```

آخرین نسخه را از گیت می‌گیرد و همان استقرار را دوباره اجرا می‌کند. داده
(`backend/data/`)، کلیدها (`backend/.env`) و پورت دست نمی‌خورند. پیش از هر تغییر
اسکیمای دیتابیس، برنامه خودش نسخه‌ای از دیتابیس در `backend/data/backups/`
می‌گیرد. کلیدهای `.env` فقط یک بار ساخته می‌شوند، چون عوض شدنشان یعنی همه‌ی
توکن‌های صادرشده و داده‌ی رمزشده از کار می‌افتد.

### نگهداری

| کار | دستور |
| --- | --- |
| لاگ زنده | `journalctl -u samaline -f` |
| راه‌اندازی مجدد | `systemctl restart samaline` |
| وضعیت | `systemctl status samaline` |
| سلامت | `curl http://127.0.0.1:8080/api/v1/health` |

لاگ در journald است که خودش چرخش و سقف حجم دارد، پس دیسک را پر نمی‌کند.

**پشتیبان:** روزی یک نسخه‌ی سازگار از دیتابیس (با API پشتیبان‌گیری آنلاین
SQLite، نه کپی خام فایل) در `backend/data/backups/daily/` ساخته می‌شود و ۱۴ نسخه‌ی
آخر می‌ماند (`DAILY_BACKUP_KEEP`). برای بازگرداندن: سرویس را متوقف کنید، نسخه را
جای `backend/data/samaline.sqlite` بگذارید و دوباره روشن کنید.

**گوشی گم‌شده (ورود دومرحله‌ای):**
`cd /opt/samaline/backend && npm run reset-2fa -- user@example.com`

### سرویس‌های لازم برای اجرا و روشن‌ماندن خودکار

سامانه برای اجرا به هیچ سرویس دیتابیسِ جداگانه‌ای نیاز ندارد؛ SQLite یک فایل
است، نه سرویس. تنها چیزی که باید روشن بماند خودِ سرویس `samaline` است، و
`scripts/deploy.sh` آن را درست تنظیم می‌کند:

- `systemctl enable samaline` → **روشن‌شدن خودکار پس از ری‌بوت**.
- `Restart=always` و `RestartSec=5` → **بازگشت خودکار اگر فرایند کرش کند**.
- با `systemctl stop/restart`، اتصال دیتابیس و صف‌ها مرتب بسته می‌شوند.

```bash
systemctl is-enabled samaline   # باید: enabled
systemctl is-active  samaline   # باید: active
```

اگر جلوی سامانه reverse-proxy برای TLS گذاشته‌اید (Caddy یا nginx)، آن هم باید
`enabled` باشد.

### امنیت در تولید

- جداسازی کامل سازمان‌ها: هیچ کاربری به فرم، انتشار، کمپین، گیرندگان یا پلن
  سازمان دیگر دسترسی ندارد (با دود تست سنجیده می‌شود).
- تغییر پلن و صدور لایسنس فقط برای مدیر کل.
- ۱۰ رمز اشتباه برای یک حساب، آن را ۱۵ دقیقه قفل می‌کند؛ کد ۲FA هم سقف تلاش دارد.
- وبهوک و اتصال CRM به شبکه‌ی داخلی سرور درخواست نمی‌زنند (SSRF).
- `PAYMENT_PROVIDER` پیش‌فرض `local` است که هر پرداختی را موفق می‌شمارد؛ چون
  پرداخت پلن را فعال نمی‌کند بی‌خطر است، ولی برای دریافت وجه واقعی `zarinpal` کنید.
- سرویس با root اجرا می‌شود تا پنل مدیر کل بتواند سرویس را ری‌استارت کند. اگر
  این امکان را نمی‌خواهید، در فایل سرویس `User=` بدهید و مالکیت پوشه را به همان
  کاربر بدهید.
